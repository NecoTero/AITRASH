# Инструкция по перестройке рабочего репозитория для Codex

## 1. Что мы строим

Один репозиторий используется как локальная рабочая система для:

- хранения внутренних стандартов — материалов, разработанных вами;
- накопления внешних стандартов — нормативов, требований и справочных материалов из внешних источников;
- регистрации версий и происхождения документов;
- извлечения из документов структурированных требований и фактов;
- сравнения документов, редакций и стратегий;
- описания и визуализации бизнес-процессов;
- разработки небольших инструментов;
- последующего создания skills, субагентов и автоматизаций.

Основное разделение данных:

```text
внутренние источники  — материалы, созданные вами;
внешние источники     — накопительная справочная и нормативная база;
структурированные данные — извлечённые требования, факты и связи;
результаты            — отчёты, сравнения, таблицы, графики и презентации.
```

Единственное обязательное логическое разделение верхнего уровня —
`internal` и `external`. При необходимости внешние материалы можно
группировать внутри каталога по издателю, владельцу, системе или типу
источника, но это только способ навигации по библиотеке.

---

## 2. Не путать два разных элемента

### `AGENTS.md`

Файл с правилами поведения Codex в этом репозитории.

Примеры правил:

- что разрешено изменять;
- когда сначала нужен план;
- где находятся исходные документы;
- куда сохранять производные результаты;
- как подтверждать факты источниками;
- как проверять изменения;
- какие действия запрещены.

### `.agents/`

Скрытая папка для skills:

```text
.agents/
└── skills/
    └── <skill-name>/
        └── SKILL.md
```

Skill — это повторяемая рабочая инструкция, например:

- зарегистрировать новый документ;
- извлечь требования из EIR;
- сравнить две редакции стандарта;
- проверить таблицу пользователей;
- описать бизнес-процесс.

Skill не является отдельным агентом. Обычно его выполняет основной Codex
в текущем диалоге.

## 3. Рекомендованная структура

Это целевая схема. Не нужно немедленно создавать все каталоги.

```text
<repo>/
├── AGENTS.md
├── README.md
├── .gitignore
│
├── .agents/
│   └── skills/
│       └── README.md
│
├── .codex/
│   ├── config.toml
│   └── agents/
│
├── knowledge/
│   ├── README.md
│   ├── 00_inbox/
│   ├── sources/
│   │   ├── internal/
│   │   └── external/
│   ├── catalog/
│   └── structured/
│
├── docs/
│   ├── architecture.md
│   ├── processes/
│   └── decisions/
│
├── outputs/
├── schemas/
├── tools/
├── apps/
├── automations/
└── evals/
```

На первом этапе не нужно создавать пустые `apps`, `automations`, `schemas`,
`tools`, `evals` или пользовательских субагентов. Они добавляются после
появления соответствующей реальной задачи.

## 4. Что куда записывать

| Место | Что хранится | Что не хранится |
|---|---|---|
| `~/.codex/AGENTS.md` | Личные правила, применимые ко всем репозиториям | Структура и особенности этой базы знаний |
| `<repo>/AGENTS.md` | Правила текущего репозитория, ограничения и проверки | Большие методики анализа документов |
| `README.md` | Краткое описание системы и инструкция человеку | Полная техническая документация |
| `knowledge/README.md` | Устройство базы знаний, типы источников, статусы и правила регистрации | Команды поведения Codex |
| `.agents/skills/<name>/SKILL.md` | Один повторяемый процесс с входами, шагами, результатом и проверкой | Общие правила безопасности |
| `.codex/agents/<name>.toml` | Узкая роль отдельного субагента | Обычный повторяемый workflow |
| `.codex/config.toml` | Технические настройки Codex | Длинные текстовые инструкции |
| `docs/architecture.md` | Фактическое устройство системы и связи компонентов | Будущая архитектура, которая ещё не реализована |
| `docs/processes/` | Описания бизнес-процессов AS-IS и TO-BE | Правила запуска Codex |
| `docs/decisions/` | Принятые решения и причины выбора | Неоформленные догадки без статуса |
| `knowledge/00_inbox/` | Новые, ещё не зарегистрированные материалы | Проверенные и опубликованные источники |
| `knowledge/sources/internal/` | Исходные материалы, разработанные вами | Производные отчёты и автоматически извлечённые данные |
| `knowledge/sources/external/` | Оригиналы нормативов и материалов из внешних источников | Ваши переработанные версии и выводы |
| `knowledge/catalog/` | Реестр источников, версий, дат, происхождения и статусов | Полные копии документов |
| `knowledge/structured/` | Извлечённые требования, факты, сущности и связи | Оригиналы документов |
| `outputs/` | Отчёты, сравнения, таблицы, графики и презентации | Источники истины |
| `schemas/` | Машиночитаемые схемы структурированных данных | Оригинальные документы |
| `tools/` | Скрипты, CLI, конвертеры и валидаторы | Ручные заметки |
| `apps/` | Отдельные приложения и интерфейсы | Сырые документы |
| `automations/` | Стабильные сценарии и пайплайны | Эксперименты, которые ещё выполняются вручную |
| `evals/` | Проверочные сценарии skills и субагентов | Рабочие документы |

## 5. Как организовать документы и знания

### `knowledge/00_inbox/`

Сюда попадают новые файлы до регистрации:

```text
новая_редакция_EIR.pdf
таблица_пользователей.xlsx
стандарт_именования.docx
```

Файл в `00_inbox` ещё не считается проверенным источником.

### `knowledge/sources/internal/`

Здесь находятся материалы, которые созданы вами:

- внутренние стандарты;
- методики;
- инструкции;
- стратегии;
- шаблоны;
- собственные регламенты.

Для значимых изменений желательно создавать новую версию, а не терять
предыдущую редакцию.

### `knowledge/sources/external/`

Здесь находится накопительная база внешних материалов:

- нормативы;
- EIR и другие требования;
- руководства;
- стандарты;
- справочные документы;
- экспорты из внешних систем.

Эти оригиналы считаются только для чтения. Их содержание не исправляется.
При необходимости создаётся отдельная заметка, структурированная запись
или производный документ.

Внутреннюю структуру `external/` следует строить по фактической коллекции.
Допустимые признаки группировки:

- тип документа;
- источник или издатель;
- система;
- тема;
- год или редакция.

Не нужно заранее навязывать единственную иерархию. Основная навигация со
временем должна опираться не только на папки, но и на каталог метаданных.

### `knowledge/catalog/`

Каталог отвечает на вопросы:

- что это за источник;
- где находится оригинал;
- внутренний он или внешний;
- кто его создал или опубликовал;
- какая это версия;
- какая редакция актуальна;
- что она заменяет;
- когда файл был зарегистрирован;
- прошёл ли он проверку;
- можно ли использовать его как источник истины.

Пример минимальной записи:

```yaml
source_id: SRC-0001
scope: external
title: Название документа
source_owner: Название автора или издателя
version: "2.0"
document_date: 2026-06-15
registered_at: 2026-07-22
path: ../sources/external/...
status: registered
supersedes: SRC-0000
```

Формат каталога нужно выбрать после анализа фактического объёма данных.
Для начала достаточно CSV, YAML или JSONL. База данных нужна только тогда,
когда файлов и связей становится действительно много.

### `knowledge/structured/`

Здесь хранятся не документы, а нормализованные записи:

- требования;
- определения;
- правила;
- роли;
- пользователи;
- стратегии;
- замечания;
- связи между источниками;
- статусы проверки.

Каждая существенная запись должна сохранять ссылку на оригинальный источник:

```text
source_id
страница или лист
раздел, пункт или диапазон ячеек
исходная цитата или исходное значение
статус проверки
```

Структурированные данные не заменяют оригиналы. Они являются удобным слоем
для поиска, сравнения, графиков, презентаций и автоматизаций.

### `outputs/`

Здесь находятся только производные результаты:

- сравнительные отчёты;
- сводные таблицы;
- презентации;
- графики;
- диаграммы;
- черновики решений;
- результаты анализа.

Результат в `outputs/` не становится источником истины только потому,
что его создал Codex.

---

## 6. Когда создавать skill

Skill создаётся только после того, как задача хотя бы один раз выполнена
понятным способом и ожидается её повторение.

Хорошие первые кандидаты:

```text
.agents/skills/source-register/SKILL.md
.agents/skills/document-compare/SKILL.md
.agents/skills/requirements-extract/SKILL.md
```

Каждый skill должен описывать:

1. Когда его применять.
2. Когда его не применять.
3. Какие входные данные требуются.
4. Какие источники нужно прочитать.
5. Последовательность действий.
6. Формат результата.
7. Как проверить результат.
8. Какие действия запрещены.

Не нужно заранее создавать десятки skills.

---

## 7. Когда создавать субагента

Субагент нужен, когда отдельная часть работы должна:

- выполняться в изолированном контексте;
- идти параллельно;
- иметь отдельные права;
- проводить независимую проверку;
- возвращать ограниченный структурированный результат.

Первый разумный субагент — read-only reviewer.

Не нужно создавать субагента только ради названия профессии или «личности».
До появления понятного сценария каталог `.codex/agents/` может оставаться
отсутствующим или пустым.

## 8. Порядок перестройки текущего репозитория

1. Проверить текущее состояние Git.
2. Найти все существующие:
   - `AGENTS.md`;
   - `.agents`, `.agents.md` и `.agents/`;
   - `SKILL.md`;
   - `.codex/config.toml`;
   - `.codex/agents/*.toml`;
   - внутренние стандарты;
   - внешние стандарты;
   - каталоги и реестры документов;
   - структурированные данные;
   - скрипты и результаты.
3. Не изменяя файлов, классифицировать их.
4. Отдельно определить:
   - внутренние оригиналы;
   - внешние оригиналы;
   - производные документы;
   - структурированные записи;
   - код;
   - инструкции Codex.
5. Найти дублирование, противоречия, устаревшие ссылки и смешение исходников
   с производными результатами.
6. Подготовить карту перемещения `старый путь → новый путь`.
7. Показать перечень создаваемых, изменяемых и перемещаемых файлов.
8. Получить подтверждение пользователя.
9. Создать минимальный каркас.
10. Перенести только подтверждённые элементы.
11. Обновить внутренние ссылки.
12. Проверить diff, ссылки и состояние Git.
13. Подготовить changelog и сообщение commit.
14. Не выполнять commit без отдельной команды.

# Запрос №1 для Codex: аудит и план

Скопируйте этот блок в Codex из корня репозитория.

```text
Режим: аудит и план.

Не создавай, не изменяй, не перемещай и не удаляй файлы на этом этапе.
Не выполняй commit.
Не устанавливай зависимости.
Не используй внешнюю сеть.
Не изменяй мой глобальный файл ~/.codex/AGENTS.md.

Цель:
привести текущий репозиторий к понятной минимальной архитектуре локальной
AEC/BIM-базы знаний для внутренних стандартов, внешних нормативов,
структурированных данных, бизнес-процессов, небольших инструментов
и будущих автоматизаций.

Не вводи дополнительные верхнеуровневые области данных без фактической
необходимости. Основное разделение источников:

- `internal` — материалы, разработанные мной;
- `external` — накопительная база материалов из внешних источников.

Сначала изучи фактическое состояние репозитория.

Проверь:

1. Текущий Git-корень и `git status`.
2. Полное дерево каталогов на разумной глубине.
3. Все существующие файлы и каталоги, относящиеся к:
   - AGENTS.md;
   - AGENTS.override.md;
   - .agents;
   - .agents.md;
   - .agents/**;
   - SKILL.md;
   - .codex/config.toml;
   - .codex/agents/*.toml;
   - README;
   - описанию архитектуры;
   - внутренним стандартам;
   - внешним стандартам;
   - нормативам и справочным документам;
   - реестрам источников и версиям;
   - структурированным требованиям и фактам;
   - scripts, tools, apps, automations, schemas и evals;
   - производным отчётам и результатам.
4. Какие найденные элементы являются:
   - правилами Codex;
   - описанием всей системы;
   - внутренним исходным документом;
   - внешним исходным документом;
   - записью каталога или метаданными;
   - структурированными данными;
   - повторяемым workflow;
   - конфигурацией субагента;
   - кодом;
   - производным результатом.
5. Дублирование, противоречия, устаревшие ссылки, неясные версии и неверно
   размещённые инструкции.
6. Случаи, где оригиналы смешаны с результатами анализа или изменёнными копиями.

Не читай содержимое секретов, токенов, `.env` и учётных данных.
Не открывай большие бинарные документы целиком, если для аудита достаточно
имени, пути, размера и типа файла.
Не меняй существующую классификацию файлов без доказанной необходимости.

Используй следующую целевую модель:

- `AGENTS.md` — правила текущего репозитория;
- `README.md` — краткое описание системы и руководство человеку;
- `.agents/skills/<name>/SKILL.md` — повторяемые workflows;
- `.codex/agents/<name>.toml` — только реальные специализированные субагенты;
- `.codex/config.toml` — техническая конфигурация Codex;
- `knowledge/README.md` — правила устройства базы знаний;
- `knowledge/00_inbox/` — новые незарегистрированные материалы;
- `knowledge/sources/internal/` — материалы, разработанные мной;
- `knowledge/sources/external/` — оригиналы из внешних источников;
- `knowledge/catalog/` — реестр источников, версий, происхождения и статусов;
- `knowledge/structured/` — извлечённые требования, факты, сущности и связи;
- `docs/architecture.md` — фактическое устройство системы;
- `docs/processes/` — описания бизнес-процессов;
- `docs/decisions/` — журнал архитектурных и рабочих решений;
- `outputs/` — производные отчёты, таблицы, графики и презентации;
- `schemas/`, `tools/`, `apps/`, `automations/`, `evals/` — создавать только
  при наличии реального содержимого или подтверждённой ближайшей задачи.

Эта структура является ориентиром, а не приказом переименовать всё.
Сначала сопоставь её с фактическими каталогами. Если существующее название
понятно и выполняет ту же функцию, предложи оставить его.

Не создавай пустую архитектуру «на будущее».
Не создавай skills, субагентов, hooks, MCP и автоматизации без реального
существующего workflow.
Не создавай вложенные AGENTS.md, если нет фактических локальных исключений.
Не предлагай дополнительные уровни разделения без фактической необходимости.

Подготовь результат в формате:

## 1. Что найдено

Таблица:
`Путь | Тип | Internal / External / Служебное | Назначение | Статус | Проблема`

## 2. Основные проблемы текущей структуры

Раздели на:
- критические;
- существенные;
- косметические.

## 3. Рекомендованная минимальная структура

Покажи только то, что действительно нужно создать сейчас.
Отдельно покажи элементы, которые следует отложить.

## 4. Карта миграции

Таблица:
`Текущий путь | Рекомендованный путь | Действие | Причина | Риск`

Допустимые действия:
- оставить;
- изменить содержимое;
- переместить;
- переименовать;
- объединить;
- архивировать;
- отложить решение.

Не предлагай удаление, если можно архивировать или оставить до ручной проверки.
Не перемещай внутренние материалы во внешние или наоборот без явного
подтверждения происхождения.

## 5. Файлы, которые будут созданы

Для каждого файла укажи:
- назначение;
- краткое содержание;
- почему он нужен сейчас.

## 6. Файлы, которые будут изменены или перемещены

Укажи влияние и способ сохранения исходного содержания.

## 7. Предлагаемое содержание ключевых файлов

Подготовь черновые структуры для:
- корневого AGENTS.md;
- README.md;
- knowledge/README.md;
- docs/architecture.md;
- .agents/skills/README.md.

Не дублируй мой глобальный ~/.codex/AGENTS.md.
Корневой AGENTS.md должен содержать только правила этого репозитория.
```

## 9. Как понять, что перестройка завершена

Результат можно принять, когда:

- существует один понятный корневой `AGENTS.md`;
- `.agents/` используется только для skills;
- внутренние и внешние источники разделены и не смешиваются;
- оригиналы отделены от структурированных данных и производных результатов;
- существует понятный реестр происхождения и версий документов либо есть
  согласованный план его создания;
- текущие документы и данные не потеряны;
- нет пустого «космолёта» из ненужных каталогов;
- существующие workflows не выданы за готовые skills без проверки;
- все перемещения видны в Git diff или `git status`;
- Codex перечислил файлы с неясным происхождением и непроверенные места;
- commit ещё не выполнен.
